# Feature Specification: Student Task Manager

**Feature Branch**: `student-task-manager`

**Created**: 2026-08-11

**Status**: Draft

**Input**: Build a simple task management REST API for students using Python and FastAPI.

## User Scenarios & Testing

### User Story 1 - Create and manage tasks (Priority: P1)
A student can create, list, update, and delete personal tasks using the API.

**Why this priority**: This is the core functionality for the task manager and delivers primary value immediately.

**Independent Test**: Verify task creation, retrieval, update, and deletion through the API without requiring additional features.

**Acceptance Scenarios**:
1. Given a student wants to add a task, when they send a valid `POST /tasks` request, then the system returns `201 Created` with the created task.
2. Given a student requests `GET /tasks`, when tasks exist, then the system returns `200 OK` with a list of tasks.
3. Given a student updates an existing task via `PATCH /tasks/{task_id}`, when the request is valid, then the system returns `200 OK` with the updated task.
4. Given a student deletes an existing task via `DELETE /tasks/{task_id}`, when the task exists, then the system returns `204 No Content`.

---

### User Story 2 - Validate task input securely (Priority: P2)
The API must reject invalid task payloads and return useful validation errors.

**Why this priority**: Secure and correct user input handling is essential to maintain API reliability and developer confidence.

**Independent Test**: Verify invalid request payloads fail with `422 Unprocessable Entity` and valid tasks are accepted.

**Acceptance Scenarios**:
1. Given a request with an empty title, when the student submits `POST /tasks`, then the system returns a validation error.
2. Given a request with malformed date values, when the student submits `POST /tasks`, then the system returns a validation error.
3. Given a partial update request via `PATCH /tasks/{task_id}` with invalid data, then the system returns a validation error and does not modify the task.

---

### User Story 3 - Provide a health check and documentation (Priority: P3)
The API exposes a health endpoint and supports generated API documentation.

**Why this priority**: A stable deployment and easy onboarding for developers are improved by self-documenting endpoints and health monitoring.

**Independent Test**: Verify `GET /health` returns `200 OK` and the FastAPI docs endpoint is available.

**Acceptance Scenarios**:
1. Given the service is running, when a user requests `GET /health`, then the response is `200 OK` with status information.
2. Given the application is started, when a developer opens `/docs` or `/redoc`, then the API documentation is visible.

---

### Edge Cases
- Handling requests for nonexistent task IDs returns `404 Not Found`.
- Deleting or updating a task that does not exist should not crash the service.
- Input validation should reject excessively long titles or descriptions.
- The task list can be empty and should still return `200 OK` with an empty array.

## Requirements

### Functional Requirements
- **FR-001**: The service must allow creating a task with a title, optional description, optional due date, and completion status.
- **FR-002**: The service must allow listing all tasks.
- **FR-003**: The service must allow retrieving a single task by its identifier.
- **FR-004**: The service must allow updating a task by its identifier.
- **FR-005**: The service must allow deleting a task by its identifier.
- **FR-006**: The service must validate task payloads and return structured errors for invalid input.
- **FR-007**: The service must expose a health check endpoint.
- **FR-008**: The service must use Python and FastAPI.

### Key Entities
- **Task**: Represents a student action item.
  - `id`: UUID generated by the service.
  - `title`: String, required, min length 1, max length 120.
  - `description`: String, optional, max length 500.
  - `due_date`: Date, optional.
  - `status`: Enum, one of `pending`, `in_progress`, `completed`. Use this field as the canonical task state; the `completed` boolean has been removed.

## Success Criteria

### Measurable Outcomes
- **SC-001**: Student tasks can be created, updated, retrieved, and deleted through the API.
- **SC-002**: Invalid input is rejected with validation errors and does not modify data.
- **SC-003**: The API exposes a `GET /health` endpoint returning service status.
- **SC-004**: Automated tests cover the core task management flows and validation behavior.

## Assumptions
 - The initial implementation uses SQLite via SQLAlchemy for persistence (durable storage) in v1.
- User authentication is out of scope for the first iteration.
- The primary interface is a REST API; no frontend is included in this phase.
- FastAPI documentation endpoints (`/docs`, `/redoc`) are acceptable as API docs.

## Clarifications
The following clarifications were provided and are now part of the specification:

- **Is `due_date` required?** No — optional.
- **Is `description` required?** No — optional.
 - **Can `status` transition (e.g. `completed` → `pending`)?** Yes, status transitions allow reverting (all transitions permitted). Use the `status` enum to represent task state.

## Error Response Schema

When endpoints return structured errors (validation or domain errors), they MUST follow this schema:

Example:

```
{
  "error": "validation_error",
  "fields": {
    "title": "required"
  },
  "message": "Task title is required"
}
```

- `error`: short machine-readable error code (e.g. `validation_error`, `not_found`).
- `fields`: optional object mapping field names to short messages or error codes.
- `message`: human-friendly error message suitable for display in clients.
- **Invalid task ID?** Return `404 Not Found`.
- **Delete behavior?** Permanently delete the task.
- **Authentication?** Not required for this version.
- **Empty title?** Reject (title is required).
- **Status values**: `pending`, `in_progress`, `completed`.

These rules are authoritative for the initial implementation and should be referenced when writing tests and implementing endpoints.
